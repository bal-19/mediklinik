## 3. Monorepo Best Practices (Node.js + TypeScript)

### Workspace Architecture
- Gunakan monorepo sebagai **source of truth** tunggal untuk app backend, frontend, dan shared packages
- Pisahkan concern dengan jelas:
  - `apps/` untuk aplikasi yang runnable/deployable
  - `packages/` untuk shared code reusable lintas app
  - `supabase/` untuk database schema, migration, dan seed
- Hindari dependency silang antar app:
  - `apps/web` tidak boleh import langsung dari `apps/api`
  - `apps/api` tidak boleh import dari `apps/web`
- Shared contract lintas app harus lewat `packages/`, terutama `packages/types`

### Dependency Management
- Gunakan dependency hanya di package yang benar-benar memakainya
- Jangan menaruh semua library di root jika hanya dipakai satu app
- Root `package.json` dipakai untuk orchestration workspace:
  - script monorepo (`dev`, `build`, `test`, `lint`)
  - dev tooling bersama bila memang lintas workspace
- Gunakan `dependencies` untuk runtime package
- Gunakan `devDependencies` untuk tooling build/test/lint
- Hindari duplicate dependency version antar workspace bila bisa dishare
- Jika menambah library baru, cek dulu apakah library itu:
  - hanya untuk `apps/api`
  - hanya untuk `apps/web`
  - layak menjadi dependency package bersama

### TypeScript Project Structure
- Wajib gunakan `tsconfig` berlapis:
  - root `tsconfig.base.json` untuk shared compiler options
  - `apps/api/tsconfig.json`, `apps/web/tsconfig.json`, `packages/*/tsconfig.json` untuk override spesifik
- Compiler options minimum:
  - `"strict": true`
  - `"noUncheckedIndexedAccess": true` bila kompatibel dengan codebase
  - `"forceConsistentCasingInFileNames": true`
  - `"noEmitOnError": true` untuk build package/library
- Gunakan path alias secara konsisten dan jangan membuat alias yang ambigu
- Pastikan tipe shared dapat di-import stabil dari package name, bukan dari relative path yang menembus workspace lain
- Hindari deep import lintas package seperti:
  - `../../../packages/types/src/...`
  - import internal file package lain yang bukan public API

### Public API & Package Boundaries
- Setiap package di `packages/` harus punya public entry point yang jelas, mis. `src/index.ts`
- Import antar workspace harus melalui public API package, bukan file internal
- Perubahan pada `packages/types` dianggap sebagai perubahan contract lintas app:
  - evaluasi impact ke `apps/api` dan `apps/web`
  - update consumer di kedua sisi bila perlu
- Jangan letakkan business logic domain bersama di frontend bila logic itu seharusnya hidup di backend
- Utility generic boleh dipindah ke `packages/` hanya jika benar-benar dipakai lintas app

### Build, Test, and Script Hygiene
- Semua script utama harus bisa dijalankan dari root workspace
- Pertahankan naming script yang konsisten:
  - `dev`
  - `build`
  - `lint`
  - `test`
  - `typecheck`
- Sebisa mungkin setiap workspace juga punya script lokalnya sendiri
- AI assistant sebaiknya menjalankan command terfokus saat mengubah area tertentu:
  - `bun run --filter @mediklinik/api ...` untuk backend
  - `bun run --filter @mediklinik/web ...` untuk frontend
- Jangan memaksa rebuild/test seluruh monorepo jika perubahan hanya lokal, kecuali perubahan menyentuh shared package atau root config

### Configuration & Environment
- Simpan env per app, jangan gabungkan semua env di root kecuali memang shared build tooling
- Jangan import `process.env` langsung ke frontend selain melalui mekanisme `VITE_*`
- Contract env yang dipakai lintas tim harus terdokumentasi di `AGENTS.md` atau `.env.example`
- Jika menambah env baru:
  - definisikan di app yang relevan
  - dokumentasikan tujuan dan batasannya
  - pastikan tidak membocorkan secret ke `apps/web`

### Code Ownership & Change Safety
- Saat mengubah shared package atau config root, anggap perubahan itu berdampak lintas workspace
- Perubahan berikut perlu verifikasi ekstra:
  - `package.json` root
  - lockfile
  - `tsconfig.*`
  - config lint/build/test shared
  - `packages/types`
- Jika sebuah perubahan bisa tetap lokal ke satu workspace, utamakan tetap lokal
- Hindari refactor besar lintas workspace kecuali memang diperlukan oleh task

## 4. Coding Conventions

### TypeScript
- Selalu gunakan TypeScript strict mode
- Hindari penggunaan `any` — gunakan `unknown` jika tipe tidak diketahui
- Semua interface/type dishare via `packages/types`
- Penamaan: `PascalCase` untuk class/interface, `camelCase` untuk variable/function
- Jika type/interface dipakai lintas app, export dari public API `packages/types`, jangan duplicate definition
- Hindari circular dependency antar file/package karena sering memicu masalah build monorepo

### NestJS (Backend)
```typescript
// Struktur module yang diharapkan:
src/
  modules/
    auth/
      auth.controller.ts
      auth.service.ts
      auth.module.ts
      dto/
        login.dto.ts
        register.dto.ts
      guards/
        jwt-auth.guard.ts
        roles.guard.ts
```

- Setiap modul memiliki: `controller`, `service`, `module`, `dto/`
- Gunakan `@UseGuards(JwtAuthGuard, RolesGuard)` pada endpoint yang butuh auth
- Gunakan `@Roles(Role.ADMIN)` decorator untuk RBAC
- Selalu validasi input dengan DTO + `class-validator`
- Gunakan `@ApiTags`, `@ApiBearerAuth`, `@ApiOperation` untuk Swagger docs
- Error: gunakan `HttpException` dari `@nestjs/common`, jangan throw raw Error
- Response format standar:
```typescript
// Success
{ success: true, data: T, message?: string }

// Error
{ success: false, message: string, errors?: ValidationError[] }
```

### React (Frontend)

- Gunakan **functional components** + hooks, tidak boleh class component
- Penamaan file component: `PascalCase.tsx`
- Gunakan `TanStack Query` untuk semua data fetching (bukan useEffect manual)
- Form selalu pakai `React Hook Form` + `Zod` schema validation
- Gunakan Shadcn/UI component sebisa mungkin sebelum buat custom
- Jangan hardcode warna — selalu gunakan Tailwind class atau CSS variable dari Shadcn theme
- Dashboard/app mengutamakan prinsip desain: **clarity**, **efficiency**, **trust**
- Gunakan token visual dari `DESIGN.md`:
  - Primary: `#0EA5E9`
  - Background: `#F8FAFC`
  - Surface: `#FFFFFF`
  - Text primary: `#0F172A`
  - Border: `#E2E8F0`
- Font UI default: `Inter`, font monospace untuk nomor antrian / ID: `JetBrains Mono`
- Layout dashboard default:
  - Sidebar fixed `240px`
  - Topbar sticky `64px`
  - Main content max-width `1280px`, padding `24px`
- Role-based UI wajib dibedakan:
  - `ADMIN`: fokus operasional harian, alert stok, antrian aktif
  - `DOCTOR`: sidebar lebih ringkas, form rekam medis distraction-free
  - `PATIENT`: mobile-first, layout sederhana tanpa sidebar kompleks
- Responsive behavior minimum:
  - `< md`: sidebar menjadi bottom navigation
  - `< md`: table diprioritaskan menjadi card list bila usability turun
  - nomor antrian publik harus tetap prominent dengan ukuran responsif

### Supabase
- **Row Level Security (RLS) wajib aktif** untuk semua tabel yang mengandung data pasien
- Migration files menggunakan naming: `YYYYMMDDHHMMSS_description.sql`
- Jangan query Supabase langsung dari frontend kecuali untuk Realtime subscription
- Semua CRUD dilakukan lewat NestJS API

## 6. Auth Flow

```
1. User POST /auth/login → dapat { accessToken, refreshToken }
2. Frontend simpan accessToken di memory (Zustand), refreshToken di httpOnly cookie
3. Axios interceptor: jika 401, otomatis hit POST /auth/refresh
4. Jika refresh juga gagal → redirect ke /login + clear store
```

  role: Role;       // 'SUPER_ADMIN' | 'ADMIN' | 'DOCTOR' | 'PATIENT'
  iat: number;
  exp: number;
}

## 8. Midtrans Integration

### Dua Lapisan Midtrans
- **Platform Midtrans**: credential dari `.env`, dipakai hanya untuk pembayaran subscription/langganan klinik ke MediKlinik
- **Klinik Midtrans**: credential disimpan terenkripsi di database per `clinic_id`, dipakai untuk pembayaran pasien ke klinik
- Credential Midtrans klinik **tidak pernah** dikirim ke frontend; backend mengambilnya berdasarkan klinik aktif pada request

### Flow Pembayaran Pasien (Per-Klinik)
```
1. Frontend klik "Bayar Online"
2. POST /invoices/:id/pay-online → backend buat Midtrans transaction
3. Backend load credential Midtrans klinik dari tabel `clinics`
4. Backend return { snap_token }
5. Frontend buka Midtrans Snap popup dengan snap_token
6. Setelah bayar, Midtrans kirim webhook ke POST /payments/webhook
7. Backend verifikasi signature, update invoice status
```

### Flow Pembayaran Subscription MediKlinik
```
1. Pengunjung pilih paket dari landing page
2. POST /subscriptions/checkout → backend buat transaksi memakai Platform Midtrans dari `.env`
3. Backend return { snap_token }
4. Frontend buka Midtrans Snap popup dengan snap_token
5. Setelah bayar, Midtrans kirim webhook ke POST /subscriptions/webhook
6. Backend aktifkan atau perpanjang subscription klinik terkait
```

### Verifikasi Webhook
```typescript
// Selalu verifikasi Midtrans signature key
const hash = crypto
  .createHash('sha512')
  .update(`${orderId}${statusCode}${grossAmount}${serverKey}`)
  .digest('hex');

if (hash !== payload.signature_key) {
  throw new UnauthorizedException('Invalid webhook signature');
}
```

- Gunakan prefix `order_id` yang jelas untuk membedakan jenis pembayaran:
  - Invoice pasien: `{CLINIC_SLUG}-INV-{id}`
  - Subscription: `{CLINIC_SLUG}-SUB-{period}`

## 9. Stock Mutation Logic

Setiap kali dokter menyimpan `prescription_items`, sistem harus:
1. Kurangi `medicines.stock_quantity` untuk setiap item resep
2. Catat di `stock_mutations` dengan `type = 'OUT'`, `reference_id = prescription_id`
3. Cek jika `stock_quantity <= min_stock_alert` → trigger notifikasi in-app

> Lakukan ini dalam **database transaction** untuk menghindari race condition.

### Web Push Notification Flow
```
1. User klik "Aktifkan Notifikasi" → browser minta permission
2. Jika granted → navigator.serviceWorker.ready.pushManager.subscribe()
3. Frontend kirim subscription object ke POST /push/subscribe
4. Backend simpan ke tabel push_subscriptions
5. Trigger event (antrian / stok) → backend kirim push via web-push library
6. Service Worker menerima 'push' event → tampilkan notification
```

### Backend Web Push (NestJS)
```typescript
// push.service.ts
import * as webpush from 'web-push';

webpush.setVapidDetails(
  'mailto:admin@mediklinik.id',
  process.env.VAPID_PUBLIC_KEY,
  process.env.VAPID_PRIVATE_KEY
);

async sendNotification(userId: string, payload: PushPayload) {
  const subscriptions = await this.getSubscriptions(userId);
  for (const sub of subscriptions) {
    await webpush.sendNotification(sub, JSON.stringify(payload));
  }
}
```

Tambahkan ke `apps/api/.env`:
```env
VAPID_PUBLIC_KEY=
VAPID_PRIVATE_KEY=
# Generate dengan: npx web-push generate-vapid-keys
```

### Online/Offline Detection
```typescript
// hooks/useOnlineStatus.ts
export function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(navigator.onLine);
  useEffect(() => {
    const on  = () => setIsOnline(true);
    const off = () => setIsOnline(false);
    window.addEventListener('online',  on);
    window.addEventListener('offline', off);
    return () => {
      window.removeEventListener('online',  on);
      window.removeEventListener('offline', off);
    };
  }, []);
  return isOnline;
}
```

Tampilkan banner `"Anda sedang offline — data mungkin belum terbaru"` jika `isOnline === false`.

### Caching Strategy
- App shell (HTML, CSS, JS): `CacheFirst`
- API calls: `NetworkFirst` dengan fallback cache
- Static assets (gambar, font): `StaleWhileRevalidate`
- Offline fallback page: `/offline.html`
- Trigger push notification minimum:
  - pasien saat posisi antrian tinggal 2 nomor lagi
  - admin saat stok menyentuh batas minimum

## 15. Subscription & Billing

### Status Lifecycle
```
TRIAL (14 hari) → ACTIVE → EXPIRED → SUSPENDED
                     ↑______________|  (perpanjang)
```

- Klinik baru default ke `subscription_status = TRIAL`
- Trial berlangsung 14 hari sejak registrasi
- Route dashboard harus dijaga server-side dan client-side:
  - hanya `TRIAL` dan `ACTIVE` yang boleh akses area `/app/*`
  - `EXPIRED` / `SUSPENDED` harus diarahkan ke halaman billing
- Landing page publik klinik `/klinik/:slug` hanya aktif jika status `TRIAL` atau `ACTIVE`
- Kirim notifikasi H-7 sebelum masa trial/langganan habis
- Admin klinik harus bisa:
  - melihat status subscription
  - memperpanjang / upgrade paket
  - mengatur credential Midtrans kliniknya sendiri saat `TRIAL` atau `ACTIVE`

## 16. Common Pitfalls — Hindari Ini

| ❌ Jangan | ✅ Lakukan |
|---|---|
| Import code langsung dari app lain | Bagikan via `packages/` atau API contract yang jelas |
| Deep relative import ke package lain | Import lewat public entry point package |
| Menaruh dependency workspace-spesifik di root tanpa alasan | Pasang dependency di workspace yang memakai |
| Ubah `packages/types` tanpa cek consumer | Anggap itu perubahan contract lintas app dan verifikasi impact |
| Tambah env frontend tanpa prefix `VITE_` | Gunakan `VITE_*` untuk env yang memang boleh diakses frontend |
| Query Supabase langsung dari React | Semua query lewat NestJS API |
| Simpan accessToken di localStorage | Simpan di memory (Zustand) |
| Expose `SUPABASE_SERVICE_ROLE_KEY` ke frontend | Hanya gunakan di backend |
| Expose credential Midtrans klinik ke frontend | Simpan terenkripsi di DB, gunakan hanya dari backend |
| Update stok tanpa transaction | Gunakan Supabase RPC / transaction |
| Hardcode base URL API di component | Gunakan `VITE_API_URL` env var |
| Skip validasi di DTO | Selalu pakai `class-validator` |
| Buat custom UI sebelum cek Shadcn | Cek Shadcn dulu, custom kalau tidak ada |
| Import Framer Motion di halaman app | Framer Motion hanya untuk landing page |
| Langsung request push permission saat load | Minta permission setelah user klik tombol |
| Deploy tanpa HTTPS | PWA & Web Push wajib HTTPS |
| Lupa generate VAPID keys sebelum deploy | Jalankan `npx web-push generate-vapid-keys` |
| Gunakan Platform Midtrans untuk pembayaran pasien | Gunakan Midtrans klinik per-tenant untuk invoice pasien |
| Izinkan dashboard tetap terbuka saat subscription expired | Pasang guard server-side + redirect ke `/billing` |
| Tampilkan data internal di `/klinik/:slug` | Batasi hanya info publik klinik & jadwal dokter |
